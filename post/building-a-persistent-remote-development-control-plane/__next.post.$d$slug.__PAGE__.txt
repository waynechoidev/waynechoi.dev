12:T41a5,<p>I built a web-based control plane for managing a development server on a private network. It keeps repositories, worktrees, long-running processes, development tools, and AI agent sessions accessible from desktop and mobile browsers while the actual work remains on a server I control.</p>
<p>The project is not yet a general-purpose product. It has been designed and tested around my Linux-based development environment, and broader installation, permission, compatibility, and recovery scenarios still need more work. Nevertheless, it has become a system I use for real development rather than a prototype built only for demonstration.</p>
<p>This post is about how that system evolved: from remote development control, to persistent AI conversations, to a major data-model redesign, and finally to a conversational interface with voice input and output. More importantly, it is about the engineering process I developed after rapid AI-assisted implementation repeatedly produced locally correct features but globally unsafe architecture.</p>
<img src="/img/remote-dev-control-plane-file-viewer.png" alt="The web control plane showing a repository and its documentation" loading="lazy" /><p><em>The file viewer keeps repository inspection inside the same interface as development sessions.</em></p>
<h2>The starting point: a browser should control work, not own it</h2>
<p>The initial problem had little to do with AI. I wanted to control a development server through a browser over a private VPN network. SSH was sufficient for individual commands, but it was not a satisfying interface for managing several projects and long-running sessions across a desktop, laptop, tablet, and phone.</p>
<p>The requirements were straightforward to describe but difficult to combine correctly:</p>
<ul>
<li>the same environment should be available from multiple browsers;</li>
<li>closing a tab must not terminate a process;</li>
<li>reconnecting from another device should recover the same state;</li>
<li>repositories, worktrees, files, Git state, and processes should share an explicit ownership model;</li>
<li>access to hosts and filesystem roots should be narrowly constrained; and</li>
<li>the mobile interface should remain useful rather than merely render a compressed desktop layout.</li>
</ul>
<p>The central architectural decision was to make the server authoritative. A browser does not own a terminal, an agent process, or a long-running operation. It subscribes to state owned by the backend and sends commands to that state. Disconnecting therefore removes a client subscription, not the underlying work.</p>
<p>That distinction shaped the rest of the system. Persistent data lives in SQLite, runtime processes remain server-owned, and clients combine an initial snapshot with scoped WebSocket updates. The interface can be reopened without pretending that a new browser connection created a new development session.</p>
<img src="/img/remote-dev-control-plane-architecture.svg" alt="Architecture diagram showing browsers connecting to a control plane that coordinates durable state, scoped streams, and external development runtimes" loading="lazy" /><p><em>Browsers observe and control server-owned state; they never become the lifecycle owner of a process or agent session.</em></p>
<img src="/img/remote-dev-control-plane-team-settings.png" alt="Team settings for a managed development worktree" loading="lazy" /><p><em>A team defines the worktree, shared rules, and session lifecycle for one development scope.</em></p>
<h2>Adding AI as a development interface</h2>
<p>Once the remote-control foundation was useful, I integrated AI agent runtimes. I did not want a separate chat application sitting beside the development environment. The agent needed to operate within the same scope as the repository, files, Git state, documents, and long-running processes.</p>
<p>Different agent runtimes expose different event shapes and lifecycle semantics. Their output may include text, reasoning summaries, tool calls, command execution, errors, or process-state changes. Rendering their raw terminal output would have coupled the UI to provider-specific formatting and made recovery unreliable.</p>
<p>I instead introduced a normalized event track. Provider adapters translate runtime output into a common set of conversation events. Durable events are stored before being published to connected clients, and each event has a stable identity so that history loading and live streaming can be merged without duplicating messages.</p>
<p>This also forced an important separation between three concepts that initially looked similar:</p>
<ol>
<li><strong>Conversation history</strong> is the durable timeline shown in the UI.</li>
<li><strong>Provider context</strong> is the model's active context, which may be compacted or reconstructed.</li>
<li><strong>Runtime state</strong> describes whether the process is working, waiting, running background work, stopped, or missing.</li>
</ol>
<p>A quiet conversation does not prove that a process is idle, and a message claiming completion does not prove that the runtime has stopped. Treating chat text as process state caused ambiguous recovery behavior, so runtime state became its own authoritative stream.</p>
<h2>Reliable messaging was harder than rendering chat</h2>
<p>The most visible symptom of an incorrect message model was a user message stuck in <code>Waiting</code>. The UI had accepted it, but the provider had not necessarily started a turn. Retrying carelessly could create duplicate turns; assuming delivery could silently lose the message.</p>
<p>I redesigned delivery around explicit states. A message is accepted into a durable path, queued for a specific session, acknowledged when the runtime takes ownership, and reconciled after reconnection. Stable client-message identities prevent a reconnecting browser from submitting the same message twice.</p>
<p>Interruption required the same level of care. Pressing Escape is not merely a UI event: it must target the correct runtime generation, stop active work when possible, and preserve a queued user message without delivering it twice. Hot reloads and process restarts exposed stale runtime bindings that had looked valid in the database but no longer pointed to a live process. Recovery therefore needed to reconcile persisted intent with observed runtime state instead of trusting either source in isolation.</p>
<p>This was the point where the project stopped being “a chat UI for a command-line tool” and became a distributed state problem, even though every component ran on one private server.</p>
<h2>Feature growth exposed the wrong schema</h2>
<p>As I added repositories, worktrees, teams, manager and member sessions, assignments, documents, resources, Git inspection, and account status, the early schema grew feature by feature. Each addition made sense locally. Together they created overlapping ownership relationships and expensive reconciliation paths.</p>
<p>The critical failure was not a single bad query. AI-generated consistency checks repeatedly scanned broad portions of the database to reconstruct relationships that should have been explicit. A workspace request could trigger relationship repair beyond the workspace being viewed, while overlapping detail streams performed their own reconciliation. When the API slowed down or terminated, reconnecting clients repeated those broad reads and amplified the load. The checks appeared defensive in isolation, but together they created the same class of outage more than once.</p>
<p>Other failures revealed the same underlying problem:</p>
<ul>
<li>a migration removed a column while older CRUD code still referenced it;</li>
<li>workspace detail and team streams returned overlapping data with different refresh behavior;</li>
<li>deleting an owner before its sessions had a defined lifecycle left stale runtime records;</li>
<li>persisted bindings survived a server restart even when the external process did not; and</li>
<li>concurrent feature work reintroduced contract fields that another change had removed.</li>
</ul>
<p>Adding retries or more validation would not have fixed this. The system needed clearer ownership boundaries.</p>
<p>I redesigned the model around lifecycle rather than screens. A workspace owns registered repositories. A repository owns worktrees. A team owns one development scope and its sessions. Agent sessions own runtime identity and conversation history. Assignments represent bounded coordination between sessions rather than becoming a second task-management system. Documents and uploaded resources belong to explicit scopes instead of being inferred from whichever page opened them.</p>
<p>The WebSocket design changed with the schema. Broad polling and overlapping detail requests were replaced by scoped streams. A workspace stream carries workspace-level structure, while a selected team subscribes to the session state it actually needs. The goal was not only fewer network requests; it was to make every update answer the question, “Who owns this state, and which clients are entitled to observe it?”</p>
<h2>How I changed my way of working with AI</h2>
<p>At the beginning, I often described a feature and allowed the agent to determine both implementation and structure. That was fast while the project was small. It became dangerous once a change crossed database migrations, contracts, API routes, runtime coordination, WebSocket payloads, and React state.</p>
<p>The repeated outages changed my role in the process. I did not respond by manually writing every line. Instead, I took direct ownership of interfaces and schemas.</p>
<p>My workflow became:</p>
<ol>
<li>inspect and report the current schema, ownership relationships, and runtime path before editing;</li>
<li>identify every contract, migration, API, stream, and UI consumer affected by the change;</li>
<li>decide the ownership boundary and compatibility strategy myself;</li>
<li>assign one owner to shared contracts and migrations so concurrent work cannot rewrite them independently;</li>
<li>implement in bounded phases, keeping the live API compatible for as long as possible;</li>
<li>verify both a fresh database and an upgraded existing database; and</li>
<li>inspect the resulting schema and interfaces again rather than accepting a successful health endpoint as proof.</li>
</ol>
<p>This is a different form of hands-on engineering. I was not merely approving generated code, nor was I delegating architecture to a model. I used AI to accelerate investigation and implementation while requiring the system's contracts to remain explainable to me.</p>
<p>The most useful review questions were architectural rather than stylistic:</p>
<ul>
<li>Can this state be derived from one authoritative source?</li>
<li>Is this relationship represented explicitly or reconstructed through scans?</li>
<li>What survives a process restart, and what must be observed again?</li>
<li>Can a migration leave the running application in an intermediate incompatible state?</li>
<li>Does a stream publish an entity it owns, or a convenient mixture assembled for one page?</li>
<li>Can delivery, interruption, and reconnection occur twice without creating two turns?</li>
</ul>
<p>Those questions prevented more defects than reviewing isolated implementation details.</p>
<h2>Integrating development tools into the same scope</h2>
<p>The browser interface grew beyond conversation because an agent's claims are not sufficient evidence of a code change. I added file inspection and a read-oriented Git viewer so I could examine the worktree, changes, and commit history without leaving the selected development scope.</p>
<img src="/img/remote-dev-control-plane-git-history.png" alt="Commit history in the integrated Git viewer" loading="lazy" /><p><em>The Git viewer exposes bounded status, diff, and commit history without making the browser a Git runtime owner.</em></p>
<p>The Git view deliberately remains read-oriented. Destructive operations belong in an explicit agent or terminal workflow where their command and scope can be reviewed. Repository paths are resolved from registered workspace data and checked against allowed roots rather than accepted directly from arbitrary browser input.</p>
<p>This separation is representative of the whole design: the UI provides observation and scoped control, while the server owns identity, authorization, and lifecycle.</p>
<h2>From text chat to a voice-enabled development session</h2>
<p>After text messaging, attachments, queuing, and interruption had a reliable path, I added voice interaction. Voice input is not a separate command system. A confirmed transcript enters the same delivery pipeline as typed text.</p>
<img src="/img/remote-dev-control-plane-voice-session.png" alt="A desktop agent conversation with compact voice controls" loading="lazy" /><p><em>Runtime state, interruption, text input, and voice controls share one conversation view.</em></p>
<p>The browser runs voice activity detection locally. Microphone frames stay in the browser until an utterance is finalized; only the completed audio segment is uploaded for server-side speech-to-text. This reduces unnecessary network traffic and avoids continuously streaming ambient audio.</p>
<p>Voice output introduced a different class of state problem. Agent responses are normalized into speakable chunks and queued in order. If the user starts speaking, tentative voice activity pauses playback without immediately destroying the queue. Only a credible finalized transcript confirms barge-in, cancels stale speech, and sends the new message. Generation identities prevent late browser callbacks from replaying cancelled audio.</p>
<img src="/img/remote-dev-control-plane-voice-settings.png" class="post-pic" alt="Voice input, playback, and microphone sensitivity settings" loading="lazy" /><p><em>Input language, output voice, playback speed, sensitivity, and notification volume are independently configurable.</em></p>
<p>Mobile constraints mattered throughout this work. The voice interface could not replace the text composer or occupy the entire screen. It became a compact panel above the existing input, preserving the same session and runtime state available on desktop.</p>
<img src="/img/remote-dev-control-plane-mobile-voice-session.png" class="post-pic" alt="A mobile agent conversation with voice controls" loading="lazy" /><p><em>The mobile layout retains runtime visibility, interruption, file attachment, text input, and voice control.</em></p>
<p>By this stage, the earlier failures had become design constraints rather than a separate list of edge cases. A persisted runtime identifier was no longer proof of a recoverable process; the coordinator had to observe the external process and reconcile it with stored intent. Bounded snapshots complemented WebSocket delivery so a client could recover after a long disconnection, and expensive consistency checks moved out of frequently requested paths.</p>
<p>Deployment and verification followed the same ownership model. I treated a migration, its shared contracts, API routes, streams, and frontend consumers as one change. I tested both fresh installations and upgrades, then exercised live streams, message delivery, runtime recovery, and the production build. With explicit schemas, lifecycle rules, and acceptance criteria in place, AI-assisted implementation became faster to review and less likely to compensate for unclear ownership with more runtime inference.</p>
<h2>Where the project stands</h2>
<p>The system now provides a persistent web control plane over a private development server, with repository and worktree inspection, durable agent conversations, scoped real-time state, recoverable message delivery, attachments, documents, Git history, and optional voice interaction across desktop and mobile clients.</p>
<p>It is still tailored to my environment, not a finished general-purpose platform. That limitation is intentional to state clearly: the interesting outcome is not that every deployment problem has been solved, but that the project has crossed the boundary from a quickly assembled personal tool into a system whose ownership model, runtime behavior, and failure modes I can explain and evolve deliberately.</p>
<p>Building it changed how I work with AI-assisted development. I still use agents extensively, but I no longer treat rapid code generation as a substitute for system design. I ask them to investigate, implement, and verify within boundaries I can reason about. The schemas, interfaces, lifecycle rules, and acceptance criteria remain mine to own.</p>
<p>That shift—from delegating code to directing a system—was the most important result of the project.</p>
